# SumDiary PRD

## 1. 문서 정보

- 제품명: SumDiary
- 문서 목적: 완성도 높은 제품 원칙, 온디바이스 AI 요약, 개인정보 보호, 법적 검토 기준, 개발 우선순위를 정리한다.
- 작성일: 2026-06-04
- 상태: 초안
- 대상 플랫폼: Android와 iOS 동시 1차 출시
- 1차 출시 국가: 대한민국

## 2. 제품 개요

SumDiary는 사용자가 하루 동안 짧게 남긴 일기 기록을 모아 일간/주간 단위로 요약해 주는 개인 기록 앱이다. 사용자는 부담 없이 여러 번 기록하고, 앱은 흩어진 기록을 읽기 쉬운 요약과 감정 키워드로 정리한다.

제품 원칙은 "처음부터 완성도 있게"이다. 기능을 많이 넣는 것보다 사용자의 가장 민감한 기록을 안전하게 다루는 구조, 신뢰 가능한 요약 경험, 법적 리스크를 낮추는 운영 체계를 먼저 완성한다.

요약 기능은 기본적으로 온디바이스 AI를 사용한다. 일기 원문은 요약을 위해 외부 AI 서버로 전송하지 않는 것을 기본 정책으로 하며, 어떤 예외도 명시적 사용자 동의와 법무 검토 없이는 허용하지 않는다.

1차 출시에는 사용자가 직접 연결하는 외부 클라우드 백업/동기화를 포함한다. SumDiary 자체 계정과 자체 백업 서버는 운영하지 않는다. 백업은 사용자가 명시적으로 켠 경우에만 동작하며, 원문 일기는 전송 전 사용자 키 기반으로 암호화하고 클라우드 연결 해제/백업 파일 삭제/동기화 해제를 제품 핵심 흐름으로 제공한다.

## 3. 문제 정의

일기 앱은 꾸준히 쓰기 어렵다. 사용자는 긴 글을 한 번에 써야 한다는 부담을 느끼고, 여러 번 짧게 기록하더라도 나중에 흐름을 되짚기 어렵다.

SumDiary는 다음 문제를 해결한다.

- 짧은 기록을 여러 번 남겨도 하루의 흐름을 쉽게 파악하기 어렵다.
- 작성한 기록이 쌓여도 주간 회고로 연결되지 않는다.
- 감정이나 주요 사건을 직접 정리하는 데 시간이 든다.
- 모바일에서 빠르게 기록하고 바로 확인할 수 있는 간결한 경험이 필요하다.

## 4. 목표

- 사용자가 10초 안에 새 일기 작성을 시작할 수 있다.
- 사용자가 오늘 작성한 일기를 한 화면에서 확인할 수 있다.
- 사용자가 오늘 요약과 이번 주 요약을 버튼 한 번으로 생성할 수 있다.
- 요약 결과는 기간, 요약문, 감정 태그를 포함한다.
- KMP 구조를 유지하여 도메인/데이터/기능 로직을 Android와 iOS에서 공유하고, 두 플랫폼을 동시에 출시한다.
- 일기 원문은 AI 요약 처리를 위해 외부 서버로 전송하지 않으며, 클라우드 백업은 사용자가 명시적으로 켠 경우에만 수행한다.
- 온디바이스 AI 요약 품질, 지연 시간, 실패 처리를 제품 수준으로 검증한다.
- 사용자가 선택한 경우 외부 클라우드 계정 기반 백업과 Android/iOS 간 동기화를 제공한다.
- 대한민국 개인정보 보호법과 Google Play/App Store 국내 제출 요건을 릴리스 게이트에 포함한다.

## 5. 비목표

- MVP에서 소셜 공유, 공개 피드, 커뮤니티 기능을 제공하지 않는다.
- MVP에서 캘린더 전체 UI, 이미지 첨부, 음성 입력, 위치 기록은 포함하지 않는다.
- 사용자의 명시적 선택 없이 원문 일기를 클라우드 AI, 분석 SDK, 로그 서버, crash report 첨부 데이터로 전송하지 않는다.
- 사용자의 명시적 선택 없이 클라우드 백업을 켜지 않는다.
- 사용자의 정신건강, 질병, 법률, 금융 상태에 대해 진단이나 전문적 조언을 제공하지 않는다.

## 5.1 제품 완성도 원칙

- Privacy by Design: 개인정보 보호를 기능 출시 이후 보완하지 않고 요구사항 단계부터 설계한다.
- On-device First: 요약, 감정 태그, 검색 색인 등 민감 데이터 처리는 가능한 한 기기 내에서 수행한다.
- Explicit Consent: 민감정보 가능성이 있는 데이터 처리는 목적, 항목, 보유 기간, 거부권을 명확히 고지하고 별도 동의를 받는다.
- Data Minimization: 기능에 필요한 최소 데이터만 저장하고, 불필요한 원문 복제와 장기 보관을 피한다.
- User Control: 사용자는 데이터 삭제, 내보내기, AI 요약 사용 여부, 백업 사용 여부를 직접 통제할 수 있어야 한다.
- Secure Sync: 클라우드 백업/동기화는 전송 구간 암호화, 백업 파일 암호화, 클라우드 연결 해제, 백업 파일 삭제, 동기화 해제를 기본 요구사항으로 둔다.
- No Dark Patterns: 동의 거부로 핵심 수동 일기 작성 기능을 과도하게 제한하지 않는다.
- Legal Gate Before Release: 개인정보 처리방침, 동의 화면, 보안 조치, 제3자 SDK, AI 모델 배포 방식을 출시 전 법무 검토한다.

## 6. 주요 사용자

### 개인 기록 사용자

- 하루에 긴 일기를 쓰기보다 짧은 메모를 여러 번 남긴다.
- 밤에 하루를 되짚거나 주말에 한 주를 회고하고 싶다.
- 복잡한 기능보다 빠른 작성과 깔끔한 요약을 선호한다.

### 회고 중심 사용자

- 감정 변화, 생활 패턴, 주요 사건을 주기적으로 확인하고 싶다.
- 일간/주간 요약을 통해 자기 이해를 돕는 기록을 원한다.

## 7. 핵심 사용자 흐름

### 7.1 일기 작성

1. 사용자가 앱을 연다.
2. "일기" 탭에서 작성 버튼을 누른다.
3. 새 일기 입력창에 내용을 입력한다.
4. 저장을 누른다.
5. 입력한 기록이 오늘의 일기 목록에 추가된다.

### 7.2 오늘 요약 확인

1. 사용자가 "요약" 탭으로 이동한다.
2. 앱이 오늘 날짜 기준 요약을 불러온다.
3. 사용자는 기간, 요약문, 감정 태그를 확인한다.
4. 사용자는 "오늘 요약" 버튼으로 다시 생성/조회할 수 있다.

### 7.3 이번 주 요약 확인

1. 사용자가 "요약" 탭에서 "이번 주 요약" 버튼을 누른다.
2. 앱은 현재 날짜를 기준으로 주간 기간을 계산한다.
3. 해당 기간의 일기를 모아 요약을 제공한다.

## 8. 기능 요구사항

### 8.1 일기 작성

- 사용자는 텍스트 기반 일기를 작성할 수 있어야 한다.
- 공백만 있는 일기는 저장하지 않아야 한다.
- 저장된 일기는 작성 날짜, 작성 시간, 내용, 고유 ID를 가져야 한다.
- 저장 후 입력창은 초기화되어야 한다.
- 같은 날짜와 시간으로 저장되는 항목은 기존 항목을 갱신할 수 있다.

### 8.2 일기 조회

- 사용자는 선택된 날짜의 일기 목록을 확인할 수 있어야 한다.
- 오늘 일기가 없을 경우 빈 상태 메시지를 표시해야 한다.
- 일기 목록은 안정적인 ID를 기준으로 렌더링되어야 한다.

### 8.3 날짜/시간

- 앱은 기기의 현재 시간대를 기준으로 오늘 날짜와 현재 시간을 계산해야 한다.
- 사용자는 향후 날짜 변경 기능을 통해 다른 날짜의 일기를 조회할 수 있어야 한다.
- MVP의 Android 화면에서는 오늘 날짜 중심으로 제공한다.

### 8.4 요약

- 사용자는 일간 요약을 생성/조회할 수 있어야 한다.
- 사용자는 주간 요약을 생성/조회할 수 있어야 한다.
- 요약 결과는 다음 정보를 포함해야 한다.
  - 요약 유형
  - 시작일
  - 종료일
  - 요약문
  - 감정 태그 목록
- 기록이 없는 기간은 기록이 없음을 알리는 문구를 표시해야 한다.
- 요약은 기본적으로 온디바이스 AI로 생성되어야 한다.
- 온디바이스 AI가 지원되지 않는 기기에서는 명확한 대체 UX를 제공해야 한다.
- 클라우드 요약 fallback은 기본 비활성화한다.
- 클라우드 요약 fallback을 도입하려면 별도 opt-in, 개인정보 처리방침 개정, 데이터 전송 국가/수탁자/보유 기간 고지, 법무 검토가 필요하다.
- AI 요약은 사용자의 삶을 해석하는 보조 기능이며, 사실 확정이나 전문적 판단으로 표현하지 않아야 한다.

### 8.5 감정 태그

- 요약 결과는 감정 태그 목록을 제공해야 한다.
- 감정 태그는 온디바이스 AI 또는 로컬 규칙 기반으로 생성한다.
- 감정 태그는 진단, 치료, 정신건강 평가처럼 보이는 표현을 피한다.
- 사용자는 감정 태그를 숨기거나 삭제할 수 있어야 한다.

### 8.6 저장소

- 일기와 요약 데이터는 로컬 저장소에 저장되어야 한다.
- 도메인 계층은 저장 구현에 직접 의존하지 않아야 한다.
- 데이터 계층은 repository interface를 구현해야 한다.
- 로컬 저장 데이터는 OS 수준 보안과 앱 수준 암호화 적용 가능성을 검토해야 한다.
- 백업 기능은 기본 비활성화하고, 사용자가 명시적으로 켜는 방식으로 설계한다.
- 클라우드 백업 데이터는 앱 안에서 사용자 키 기반으로 암호화한 뒤 외부 클라우드에 업로드한다.
- 클라우드 백업 데이터 삭제는 로컬 삭제와 별도로 사용자가 이해할 수 있게 제공한다.
- 로그, analytics, crash report에는 일기 원문, 요약문, 감정 태그가 포함되지 않아야 한다.

### 8.7 외부 클라우드 연결

- 1차 출시는 SumDiary 자체 계정 생성과 자체 로그인을 제공하지 않는다.
- 사용자는 1차 출시에서 Google Drive 계정을 연결할 수 있어야 한다.
- 사용자는 외부 클라우드를 연결하지 않고도 로컬 일기 작성 기능을 사용할 수 있어야 한다.
- 클라우드 백업/동기화는 외부 클라우드 연결 사용자에게만 제공한다.
- 사용자는 앱 안에서 외부 클라우드 연결을 해제할 수 있어야 한다.
- 사용자는 앱 안에서 외부 클라우드에 저장된 SumDiary 백업 파일 삭제를 시작할 수 있어야 한다.
- 외부 클라우드 계정 자체의 삭제는 각 클라우드 제공자 정책과 UI에서 수행됨을 명확히 안내한다.
- Google Drive API 사용 시 최소 권한 scope만 요청하고, 앱 전용 폴더 또는 앱이 생성한 파일 범위로 접근을 제한한다.
- Dropbox와 iCloud Drive는 1차 출시 이후 후속 provider 후보로 둔다.

### 8.8 클라우드 백업 및 동기화

- 클라우드 백업은 opt-in으로 제공한다.
- 사용자는 백업 켜기 전 백업되는 데이터 항목, 암호화 방식, 연결되는 외부 클라우드 제공자, 삭제 방법을 확인해야 한다.
- 동기화 대상은 일기 원문, 요약문, 감정 태그, 사용자 설정으로 정의한다.
- 동기화 충돌이 발생하면 최신 수정 시간, 기기 ID, 사용자 선택 기준 중 하나로 해결 정책을 명확히 정한다.
- Android와 iOS 간 동기화 결과는 동일해야 한다.
- 네트워크 실패, 외부 클라우드 인증 만료, 저장 용량 초과, API 오류는 사용자에게 복구 가능한 상태로 표시한다.
- 사용자는 클라우드 백업을 끄고 외부 클라우드에 저장된 암호화 백업 파일을 삭제할 수 있어야 한다.
- 외부 클라우드 저장소 제공자, OAuth scope, API 접근 범위, 사용자가 삭제해야 하는 데이터 범위는 개인정보 처리방침과 스토어 개인정보 신고에 반영한다.

### 8.9 온디바이스 AI

- Android 구현은 Gemini Nano, ML Kit GenAI API, Google AI Edge/LiteRT, 또는 기기 내 실행 가능한 모델 배포 방식을 비교 검토한다.
- iOS 구현은 Apple Foundation Models, Core ML 기반 자체 모델, 또는 iOS 기기 내 실행 가능한 모델 배포 방식을 비교 검토한다.
- 1차 출시 권장 전략은 Android는 Gemini Nano/AICore 기반 ML Kit GenAI API, iOS는 Apple Foundation Models framework를 우선 사용한다.
- LiteRT/Core ML 기반 자체 생성 모델 배포는 1차 출시 범위에서 제외하고, 플랫폼 네이티브 모델의 한국어 품질 또는 지원 기기 범위가 부족할 때의 후속 연구 과제로 둔다.
- 온디바이스 AI 접근은 shared 도메인 계층의 공통 interface 뒤에 숨기고, Android/iOS별 구현체를 분리한다.
- 온디바이스 AI 미지원 기기에서는 클라우드 fallback을 자동으로 사용하지 않는다.
- 미지원 기기에서는 명확한 안내와 함께 로컬 규칙 기반 간단 요약 또는 요약 비활성화 UX를 제공한다.
- 모델은 일기 요약에 충분한 품질을 제공하면서도 배터리, 저장 용량, 지연 시간을 과도하게 소모하지 않아야 한다.
- 모델 다운로드가 필요한 경우 사용자가 용량, 네트워크 조건, 삭제 가능 여부를 이해할 수 있어야 한다.
- 모델 실행 입력은 필요한 기간의 일기 텍스트로 제한한다.
- 모델 출력은 요약문과 감정 태그의 구조화된 결과를 목표로 한다.
- 모델 실패, 미지원 기기, 모델 미설치, 리소스 부족 상황을 제품 UX로 처리한다.
- 모델 업데이트로 요약 결과가 달라질 수 있음을 제품 정책에 반영한다.

### 8.10 개인정보 및 법적 요구사항

- 일기 원문은 민감정보가 포함될 가능성이 높은 데이터로 취급한다.
- 개인정보 처리 목적, 처리 항목, 보유 기간, 파기 방법, 정보주체 권리 행사 방법을 개인정보 처리방침에 명시한다.
- 민감정보 처리가 필요한 경우 일반 개인정보 동의와 구분된 별도 동의 UX를 제공한다.
- 만 14세 미만 사용자를 허용할 경우 법정대리인 동의와 아동 개인정보 보호 절차를 설계한다.
- 자동화된 결정에 해당할 가능성이 있는 기능은 사용자의 권리 또는 의무에 중대한 영향을 주지 않도록 제한한다.
- AI 요약 기준, 처리 방식, 사용자가 요청할 수 있는 설명/삭제/처리정지 절차를 쉽게 확인할 수 있게 한다.
- 제3자 SDK는 수집 항목, 전송 국가, 수탁자, 보유 기간, opt-out 가능 여부를 검토한 뒤 도입한다.
- 개인정보 유출 대응 절차, 사용자 통지 절차, 내부 담당자, 증적 보관 절차를 운영 문서로 둔다.

### 8.11 플랫폼

- Android 앱은 Compose 기반 UI를 제공한다.
- iOS 앱은 SwiftUI 기반 UI를 제공한다.
- iOS 앱은 shared 모듈의 factory 및 공통 로직을 재사용해야 한다.
- 공통 도메인/데이터/기능 로직은 KMP shared 모듈에 유지한다.
- Android와 iOS는 동일한 핵심 사용자 흐름, 동일한 개인정보 보호 원칙, 동일한 온디바이스 AI 정책을 제공해야 한다.

## 9. 비기능 요구사항

- 앱 시작 후 주요 화면은 지연 없이 표시되어야 한다.
- 일기 저장은 사용자가 체감할 수 있을 정도로 빠르게 완료되어야 한다.
- 요약 생성 중에는 loading 상태를 표시해야 한다.
- 오프라인 상태에서도 로컬 작성과 기존 데이터 조회가 가능해야 한다.
- 외부 클라우드 연결/백업 기능이 실패해도 로컬 작성 기능은 계속 사용할 수 있어야 한다.

- 날짜 계산은 사용자 로컬 시간대를 기준으로 일관되게 처리되어야 한다.

- AI 실행 중 배터리, 발열, 메모리 압박을 모니터링하고 과도한 반복 실행을 제한해야 한다.
- 원문 데이터는 디버그 로그, exception message, analytics event, screenshot capture에 포함되지 않아야 한다.
- 삭제 요청 시 로컬 원문, 요약, 색인, 캐시를 함께 삭제해야 한다.
- 외부 클라우드 연결 해제 또는 백업 파일 삭제 요청 시 처리 상태를 사용자에게 알려야 한다.

## 11. 성공 지표

## 15. 주요 의사결정 필요 항목

- 앱의 1차 출시 플랫폼은 Android와 iOS 동시 출시로 확정한다.
- Android 온디바이스 AI는 Gemini Nano/AICore 기반 ML Kit GenAI API 우선으로 확정한다.
- iOS 온디바이스 AI는 Apple Foundation Models framework 우선으로 확정한다.
- LiteRT/Core ML 기반 자체 생성 모델은 1차 출시 이후 연구 과제로 둔다.
- SumDiary 자체 계정과 자체 백업 서버는 1차 출시에서 제외한다.
- 1차 출시 클라우드 백업 provider는 Google Drive 단독으로 확정한다.
- Dropbox와 iCloud Drive는 1차 출시 이후 후속 provider 후보로 둔다.
- 클라우드 백업 암호화는 사용자 키 기반 end-to-end encryption 방식으로 확정한다.
- 1차 출시에서 지원할 외부 클라우드 제공자 조합을 결정한다.
- 일기 데이터의 민감도를 고려해 앱 잠금, 암호화, 백업 정책의 세부 수준을 결정한다.
- 주간 요약의 주 시작일을 월요일로 할지, 사용자 locale 기준으로 할지 결정한다.
- 감정 태그의 표현 방식을 한국어 고정으로 할지 다국어 대응할지 결정한다.
- 만 14세 미만 사용자를 허용할지 차단할지 결정한다.
- 1차 출시 국가는 대한민국 단독으로 확정한다.

## 16. 리스크

- 개인 일기 데이터는 민감 정보이므로 저장/백업/AI 전송 정책이 명확해야 한다.
- 온디바이스 AI는 기기별 지원 여부, 모델 품질 편차, 저장 용량, 배터리, 발열 리스크가 있다.
- 날짜/시간대 처리가 잘못되면 일기 조회와 주간 요약 범위가 어긋날 수 있다.
- 요약 품질이 낮거나 사용자의 감정을 단정하면 제품 신뢰가 떨어질 수 있다.
- 자유 입력 일기에는 민감정보와 제3자 개인정보가 포함될 수 있어 법적/윤리적 리스크가 높다.
- 외부 클라우드 API 또는 외부 SDK를 도입하는 순간 개인정보 처리 범위가 넓어진다.
- 외부 클라우드 연결 해제, 백업 파일 삭제, OAuth 권한 해제가 불완전하면 Google Play와 Apple App Store 심사 거절 가능성이 높다.
- 자체 서버를 운영하지 않더라도 앱이 암호화 전 원문을 처리하고 외부 클라우드 업로드를 수행하므로 개인정보 처리 책임이 남는다.

## 17. 릴리스 체크리스트

- 일기 저장 후 앱 재시작 시 기록이 유지된다.
- 일기가 없는 날의 빈 상태가 정상 표시된다.
- 오늘 요약이 오늘 날짜의 기록만 사용한다.
- 이번 주 요약이 의도한 주간 범위의 기록만 사용한다.
- 요약 로딩 상태가 표시된다.
- 네트워크가 꺼져 있어도 온디바이스 요약이 동작하거나 미지원 사유가 명확히 표시된다.
- 외부 클라우드를 연결하지 않아도 로컬 일기 작성이 가능하다.
- 외부 클라우드 연결 사용자는 Android/iOS 간 데이터 동기화가 가능하다.
- 클라우드 백업을 끄고 외부 클라우드의 암호화 백업 파일을 삭제할 수 있다.
- 앱 안에서 외부 클라우드 연결을 해제할 수 있다.
- 일기 원문이 로그, analytics, crash report에 포함되지 않는다.
- 전체 데이터 삭제 시 원문, 요약, 캐시, 색인이 삭제된다.
- 개인정보 처리방침과 동의 화면이 최신 기능과 일치한다.
- 민감정보 별도 동의가 필요한 경우 일반 동의와 분리되어 있다.
- 제3자 SDK와 모델 배포 방식에 대한 법무 검토가 완료되어 있다.
- Android 앱이 깨끗하게 빌드된다.
- iOS 앱이 깨끗하게 빌드된다.
- GitHub Actions CI가 PR에서 Android/KMP 기본 검증을 수행한다.
- Android와 iOS의 기본 기능 parity가 확인된다.
- 기본 접근성 라벨과 터치 영역을 점검한다.

### 18.1 한국 개인정보 보호법 기준

- 일기 원문은 건강, 성생활, 정치적 견해, 신념 등 민감정보가 포함될 수 있으므로 민감정보 가능성이 높은 데이터로 분류한다.
- 민감정보를 처리하는 경우 수집ㆍ이용 목적, 항목, 보유 및 이용 기간, 동의 거부권 및 불이익을 별도로 고지하고 동의를 받아야 한다.
- 개인정보 처리방침에는 처리 목적, 처리 항목, 보유 기간, 파기 절차, 제3자 제공, 처리 위탁, 정보주체 권리 행사 방법, 안전성 확보 조치를 포함한다.
- 온디바이스 AI라 하더라도 앱이 개인정보를 수집ㆍ저장ㆍ이용하면 개인정보 처리에 해당할 수 있으므로 "서버로 보내지 않는다"만으로 법적 검토가 끝나지 않는다.
- AI 요약이 사용자에게 중대한 영향을 주는 자동화된 결정으로 오해되지 않도록 제품 문구와 기능 범위를 제한한다.

### 18.2 해외 출시 보류 기준

- 1차 출시는 대한민국 단독으로 제한한다.
- 미국, EU, 일본 등 해외 출시 전에는 해당 지역의 개인정보, 소비자 보호, AI, 아동 개인정보, 앱 스토어 정책을 별도로 재검토한다.
- EU 출시 시 GDPR의 개인정보, 특수범주 개인정보, 프로파일링, 자동화 처리, DPIA 필요성을 검토한다.
- 미국 캘리포니아 대상 서비스가 일정 기준을 충족하면 CCPA/CPRA상 민감 개인정보, 삭제권, 알 권리, 공유/판매 opt-out, 민감정보 사용 제한을 검토한다.
- 출시 국가가 늘어날 때마다 개인정보 처리방침, 동의 UX, 데이터 주체 권리 처리 절차를 지역별로 업데이트한다.

### 18.3 제품 내 금지사항

- 일기 원문을 외부 AI API로 기본 전송하지 않는다.
- 일기 원문을 analytics event, crash log, remote config, A/B test payload에 포함하지 않는다.
- 사용자의 동의 없이 광고 타겟팅, 프로파일링, 제3자 제공에 일기 내용을 사용하지 않는다.
- 감정 태그를 정신건강 진단, 질병 예측, 법적/의학적 판단처럼 표현하지 않는다.
- 제3자 SDK를 "편의상" 추가하지 않는다. 모든 SDK는 데이터맵과 법무 검토 후 추가한다.

### 18.4 출시 전 필수 산출물

- 개인정보 데이터맵
- 개인정보 처리방침
- 민감정보 별도 동의 문안
- 온디바이스 AI 처리 설명 문안
- 외부 클라우드 백업 처리 설명 문안
- 백업 암호화/복구 키 정책
- 로그/분석 금지 필드 목록
- 데이터 삭제/내보내기 정책
- 외부 클라우드 연결 해제 및 백업 파일 삭제 정책
- 유출 대응 프로세스
- 제3자 SDK 검토표
- 앱 마켓 개인정보 라벨/데이터 보안 섹션
- 법무 검토 완료 기록

## 19. 앱 스토어 심사 대응 체크리스트

이 섹션은 Google Play와 Apple App Store 제출 시 거절 가능성을 줄이기 위한 제품 요구사항이다. 스토어 정책은 자주 변경되므로 제출 전 최신 공식 문서를 다시 확인한다.

### 19.1 공통 심사 리스크

- 개인정보 처리방침 URL은 앱 제출 전 공개적으로 접근 가능해야 하며 404, 비공개, 임시 페이지이면 안 된다.
- 스토어 설명, 스크린샷, 개인정보 라벨, 앱 내 고지, 실제 네트워크 동작이 서로 일치해야 한다.
- "온디바이스 AI", "AI 요약을 위해 일기 원문을 외부 서버로 전송하지 않음", "백업은 사용자가 켠 경우에만 수행" 같은 문구를 쓰려면 실제 구현, 로그, SDK, crash report, 백업 설정이 그 문구와 일치해야 한다.
- AI 요약 결과는 보조 정보로 표시하고, 의학적/정신건강 진단이나 치료 조언처럼 보이는 표현을 금지한다.
- 사용자가 직접 입력한 일기 원문이 포함된 화면을 스토어 스크린샷에 넣지 않는다. 샘플 데이터는 명확히 가상 데이터로 작성한다.
- 앱 이름, 설명, 키워드에 "치료", "진단", "우울증 판단", "정신건강 검사"처럼 의료/건강 심사로 확대될 표현을 사용하지 않는다.
- AI가 생성한 부적절하거나 위험한 문구를 사용자가 신고/피드백할 수 있는 경로를 앱 안에 제공한다.
- 앱 내 문의/지원 경로, 개인정보 문의 경로, 삭제 요청 경로를 제공한다.
- 모든 기능은 심사자가 재현 가능해야 하며, 외부 클라우드 연결 기능은 리뷰어 노트에 테스트 방법과 미연결 상태 UX를 설명한다.
- beta, placeholder, TODO, 미완성 화면, 깨진 링크, 임시 개인정보처리방침을 제출 빌드에 포함하지 않는다.

### 19.2 Google Play 대응

- Play Console Data safety form을 반드시 작성하고, 앱 및 제3자 SDK가 수집/공유하는 데이터와 정확히 일치시킨다.
- Google Play는 개발자가 Data safety 답변의 정확성과 완전성에 책임진다고 보기 때문에, "서버로 전송하지 않음"을 주장하려면 네트워크 캡처와 SDK 검토 증적을 보관한다.
- 앱이 개인 및 민감 사용자 데이터를 다루면 수집, 사용, 공유를 사용자 예상 범위의 앱 기능과 정책상 허용 목적에 한정한다.
- 개인 및 민감 사용자 데이터는 판매하지 않는다.
- 민감정보 처리나 사용자가 예상하기 어려운 데이터 처리가 있으면 prominent disclosure와 consent를 앱 안에서 별도로 제공한다.
- 생성형 AI 정책 적용 가능성에 대비해 AI 결과 신고/flagging 기능을 제공한다.
- AI 결과가 자해, 폭력, 아동 착취, 기만행위, 괴롭힘, 불법행위 조장으로 이어지지 않도록 안전 문구와 출력 필터링을 둔다.
- target SDK, 권한 선언, Data safety, 개인정보처리방침, 앱 콘텐츠 설문, 콘텐츠 등급 설문을 출시 전 동기화한다.
- Google Drive API를 사용할 경우 앱 기능에 필요한 최소 scope를 요청하고, 가능하면 앱 전용 폴더 또는 앱이 생성한 파일 범위로 제한한다.
- Google OAuth 검증이 필요한 scope를 요청하는 경우 검증 소요 시간과 데모 영상/개인정보처리방침 요구사항을 출시 일정에 반영한다.
- 초기 출시는 closed testing/internal testing으로 실제 기기 안정성, 미지원 기기 UX, 온디바이스 모델 다운로드 실패를 검증한다.

### 19.3 Apple App Store 대응

- App Store Connect의 App Privacy 답변은 앱과 제3자 SDK가 수집하는 모든 데이터 유형을 반영해야 한다.
- Apple은 앱 개인정보 답변을 신규 앱과 업데이트 제출에 요구하므로, 기능 변경 시 App Privacy도 함께 업데이트한다.
- 앱은 제출 전에 실제 기기에서 안정성을 검증하고, crash 또는 명백한 기술 문제가 없어야 한다.
- 앱 메타데이터, 설명, 스크린샷, 프리뷰는 실제 핵심 경험을 정확하게 보여줘야 한다.
- 숨겨진 기능, 문서화되지 않은 기능, 심사자가 접근할 수 없는 기능은 Notes for Review에 구체적으로 설명한다.
- Apple은 개인정보 보호를 핵심 기준으로 보기 때문에, 일기 데이터 처리 목적 변경이나 재사용은 추가 동의 없이는 하지 않는다.
- 건강/의료 영역으로 오해될 수 있는 기능은 피한다. 감정 태그는 "자가 회고 보조"로 표현하고, 진단/치료/위험 예측 문구를 금지한다.
- iOS에서 HealthKit, iCloud, analytics, crash SDK를 도입하는 경우 건강/개인정보 제한과 App Privacy 라벨을 별도로 검토한다.
- iCloud Drive는 1차 출시 범위가 아니며, 후속 지원 시 사용자의 iCloud 계정과 앱 접근 제어가 Apple 설정에 종속됨을 명확히 안내한다.
- 미성년자 대상 앱으로 보이게 만드는 표현을 피하거나, 아동 대상이면 Kids/아동 개인정보 요구사항을 별도 충족한다.

### 19.4 출시 전 증적 패키지

- 개인정보처리방침 URL 정상 접근 캡처
- Google Play Data safety 답변 초안
- App Store Privacy Nutrition Label 답변 초안
- 제3자 SDK 목록과 각 SDK 데이터 수집 범위
- Google Drive 권한 scope 검토표
- 네트워크 캡처 결과
- crash/analytics 로그 샘플과 원문 미포함 증명
- 온디바이스 AI 처리 설명 화면 캡처
- AI 결과 신고/피드백 화면 캡처
- 데이터 삭제 플로우 테스트 결과
- 외부 클라우드 연결 해제/백업 파일 삭제 테스트 결과
- 리뷰어 노트 초안
- 콘텐츠 등급 설문 답변 초안
- 실제 기기 QA 결과
